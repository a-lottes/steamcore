## 1. Problem & Goal

- **Problem:** `galactic-invasion`'s `score_` lives only in RAM for the current round and is explicitly lost at `GAME_OVER`/restart — its own spec names this outright (NFR-8: "score/lives exist only in RAM... never persisted"). README's *Highscore-System* section (a top-5-per-game mockup, 3-letter initials, "Speicherung... im internen Flash") remains an unbuilt Phase-2/3 checklist item, and constitution §6 already carries a non-negotiable ("persisted data carries a format version") written specifically in anticipation of this feature — nothing has used it yet.
- **Goal:** A reusable Highscore System — persisted per-game top-5 table, arcade-style initials entry, a top-5 display screen — actually wired to galactic-invasion so a good round means something the next time the console powers on, not just infrastructure that compiles.
- **Success signal:** A host test drives galactic-invasion through a full round to a qualifying score, drives the initials-entry input sequence to completion, asserts the top-5 table now contains the new entry at the correct rank, then reconstructs the storage layer against the same backing bytes (the host's stand-in for a power cycle) and asserts the entry is still there, byte-identical, on replay. A second assertion seeds corrupt/wrong-version bytes and confirms a clean empty table results, never a crash or garbage display. Deferred hardware signal: a human plays a real round, enters initials on the real device, power-cycles it, and the entry survives (A15).
- **Why now:** Named directly by the user; the one real game this platform has already hit the exact gap this feature closes (its own NFR-8); README's Highscore-System checklist item and constitution §6's anticipatory non-negotiable have both been sitting unaddressed since project kickoff.

## 2. Target Users

- **The console player who just finished a galactic-invasion round (primary):** wants a good score to be worth something beyond the current session — to see their initials on the list, and to still see them there next time the console is turned on.
- **Future game-module author (secondary):** Steam Racer / The Great Machine / Airship Battle / Mine Runner each need a per-game highscore table eventually; this feature's API should be reusable by any of them without modification, even though only galactic-invasion is wired up now (US-6).
- *Not a user of this feature:* a player choosing among multiple games' highscore lists via a menu — no second game and no game registry exist (constitution §3 "Games"), and the user's own idea text explicitly defers this to game #2, matching `start-screen` A1/`galactic-invasion` A8's own precedent exactly.

## 4. User Stories

### US-1 (Must): The Highscore System persists a per-game top-5 table, format-versioned, across power loss and reset

> As a console player who just set a good score, I want my result to still be there next time the console powers on, so a good round means something beyond the current session.

**Acceptance criteria:**

- [ ] AC-1.1: Given a game reports a final score for its own table (identified per US-6) via the system's public entry point, when that score is strictly greater than 0 (A7) and either the table holds fewer than 5 entries or the score is strictly greater than the table's current lowest of 5 entries, then a new entry (3 initials + score) is inserted at the correct rank, lower entries shift down one, and anything falling past rank 5 is discarded. A score of exactly 0 never qualifies, even into a completely empty slot on a never-played table (A7).
- [ ] AC-1.2: Given entries have been recorded, when the storage layer is freshly reconstructed against the same backing bytes (the host test's stand-in for a power cycle — no OS reboot exists to actually perform on host), then the exact same table (order, initials, scores) reads back unchanged.
- [ ] AC-1.3: Given the persisted block's format-version field doesn't match the current version, or the block fails an integrity check (unwritten/corrupt bytes), when the system reads it, then it initializes a clean, empty table rather than ever treating those bytes as valid entries or crashing (constitution §6 non-negotiable) — verified by a host test seeding both a wrong-version block and a corrupt one, confirming clean recovery in both cases.
- [ ] AC-1.4: Given the delivered code, when inspected, then it uses no dynamic allocation, no ESP-IDF header, and no filesystem/SQL-engine dependency (constitution §2 `has-database`, §3, §4) — a fixed-size, compile-time-sized store; the concrete flash-write mechanism (A5) is verified by source reading once `/sprint-plan` chooses it, not required on the host gate.
- [ ] AC-1.5 (Should, hardware-gated per A15): Given the production storage mechanism is wired to real flash, when a human power-cycles the real board after recording an entry, then the entry is still present after boot — reported `blocked` with reason if this step isn't reached this increment, never silently skipped or marked passed.

### US-2 (Must): A player enters 3-letter arcade-style initials using only GameInput's existing signals

> As a player who just earned a qualifying score, I want to type my initials the classic arcade way, so I can claim credit for it without a keyboard this console doesn't have.

**Acceptance criteria:**

- [ ] AC-2.1: Given a qualifying score is reached (US-1/AC-1.1) as a consuming game's round transitions to its end-of-round state (mirroring the existing convention, e.g. `galactic-invasion`'s AC-5.3/AC-11.2), when the next tick renders, then the initials-entry screen appears instead of that game's own end-of-round screen (A8), composed top-to-bottom of: a fixed header label reading `HIGH SCORE` (a compile-time-fixed literal, drawn in the shipped 43-glyph font — space, `!-.:0-9>?`, `A`-`Z`; F1/C10); the final score directly beneath it; the three letter positions on their own line beneath the score, each starting at 'A' (A11); and the active-letter indicator (the resolved mechanism, NFR-7/R1/C13) beneath the active position only. These elements are proven mutually disjoint at compile time against the score's worst-case rendered width (A14's 5-digit bound) — never against a fixed pixel position that assumes the runtime-actual, possibly-shorter score string's width (R2 — left for `/sprint-plan` to implement, not re-solved here). No separate end-of-round beat is ever shown first on a qualifying round, and no outcome (WIN/LOSS) text is shown on this screen (F3/C12, reconfirming A8/C8).
- [ ] AC-2.2: Given the screen is active and a rising edge of `input.up` (or `input.down`) occurs, when that tick runs, then the active position's letter advances (or retreats) exactly one step through A–Z, wrapping Z→A (or A→Z) — never a character outside A–Z, never more than one step per rising edge (holding the button does not auto-repeat).
- [ ] AC-2.3: Given a rising edge of `input.fire` occurs while the screen is active, when that tick runs, then the active position's letter locks in and the active position advances; locking in the third position submits all three letters as the entry's initials (AC-1.1) that same tick.
- [ ] AC-2.4: Given `input.start` is pressed at any point while this screen is active, then it has no effect here — its existing restart semantics (`game_state.h`) are never reused or reinterpreted on this screen (A12). No on-screen hint distinguishes this from an unresponsive device — a consciously accepted tradeoff, not an oversight (F2/C11, §6).
- [ ] AC-2.5: Given the same fixed input sequence run twice from a freshly-opened initials-entry screen, when the resulting letter/cursor sequence is compared, then it is byte-identical (constitution §4 determinism).

### US-3 (Must): The top-5 list is shown once a new entry is recorded

> As a player who just entered my initials, I want to see the updated list right away, so I know exactly where I landed.

**Acceptance criteria:**

- [ ] AC-3.1: Given the third initial locks in (AC-2.3), when the next tick renders, then a top-5 screen appears: the table's per-game display name as a header, and every occupied rank as one line (rank, initials, score), via the shipped `drawText` only.
- [ ] AC-3.2: Given the table holds fewer than 5 entries, when this screen renders, then only occupied ranks are drawn — no placeholder row for an empty slot.
- [ ] AC-3.3: Given the top-5 screen is displayed and a rising edge of `input.start` occurs, when that tick runs, then the flow proceeds into the consuming game's own existing one-button restart path (e.g. galactic-invasion's AC-6.3/AC-11.4) unchanged — no further intermediate screen.

### US-4 (Should): A non-qualifying round's existing end-screen flow is unaffected

> As a player whose score didn't make the top 5, I want the game to end exactly like it always has, so this feature never gets in the way of playing again quickly.

**Acceptance criteria:**

- [ ] AC-4.1: Given a round ends with a score that does not qualify (AC-1.1 evaluates false, including any score of exactly 0 — A7), when the next tick renders, then the consuming game's own existing end screen renders exactly as before this feature existed — the only scenario in which that screen still appears (A8) — no initials-entry or top-5 screen appears, and restart works exactly as already specified there.

### US-5 (Must): galactic-invasion reports its final score, closing its own NFR-8 gap

> As the console player finishing a galactic-invasion round, I want my score to actually reach the Highscore System, so the score I fought for isn't just gone the moment I see GAME OVER.

**Acceptance criteria:**

- [ ] AC-5.1: Given a galactic-invasion round reaches `GAME_OVER` (win or loss), when that tick's transition happens, then the round's final score is reported to the Highscore System's public entry point exactly once — verified by a host test asserting the reported value equals the score shown on that same tick's screen.
- [ ] AC-5.2: Given the diff that makes AC-5.1 possible, when reviewed, then `galactic_invasion.h`'s public surface gains at most one narrowly-scoped additive member serving exactly this purpose — no accessor for lives, formation state or any other private detail is added, and galactic-invasion's own NFR-5 claim ("no accessor for score...") is explicitly amended, not silently contradicted, to record this one deliberate exception (mirroring how the constitution itself is amended rather than silently violated).
- [ ] AC-5.3: Given galactic-invasion's own already-shipped, released acceptance criteria (spec US-1 through US-12), when this integration ships, then its existing host test suite still passes unchanged — no regression to a released, reviewed feature.

### US-6 (Should): The Highscore System's public API is reusable by a future second game without modification

> As a future game-module author, I want a ready-made highscore table I can report into, so I don't invent my own storage or initials-entry screen per game.

**Acceptance criteria:**

- [ ] AC-6.1: Given the system's public entry point, when inspected, then a caller identifies its own table via an explicit per-game identifier/display-name parameter — no game-specific name or logic hardcoded inside the system's own implementation beyond that parameter (library lens).
- [ ] AC-6.2: Given only one real consuming game exists today, when this story is verified, then a host test exercises the API with two distinct synthetic identifiers side by side and confirms their tables never cross-contaminate — satisfying this story without a second real game shipping.

## 6. Out of Scope

- **Namespace ruling for `steamcore::games`** — explicit user deferral to game #2 (A1).
- **Multi-game selection menu** — explicit user deferral to game #2 (A2).
- **A generic, registry-driven highscore browser, or any way to view a table outside the post-entry flow (US-3)** — resolved out of scope (A9/C9): the post-entry display (US-3) is the only Must-have trigger this cycle.
- **A distinct end-of-round beat (e.g. a transitional "GAME OVER"/"YOU WIN" frame) before initials entry on a qualifying round** — resolved out of scope (A8/C8): initials entry appears immediately in that screen's place, with its own header showing the final score.
- **On-screen hints or captions for the repurposed up/down/fire control scheme, and any visible feedback distinguishing an intentionally inert `start` press (AC-2.4) from an unresponsive device** — consciously accepted tradeoff (F2/C11), consistent with Principle 4 ("no text the player must read to begin"); not an oversight.
- **Outcome (WIN/LOSS) text on the initials-entry screen for a qualifying round** — reconfirmed out of scope (F3/C12): the screen's header shows only the score (AC-2.1), matching A8/C8's original resolution exactly; a non-qualifying round's own end screen remains the only screen that ever shows outcome text (US-4).
- **MicroSD storage** — README names this as a possible *later* extension, not required now.
- **Sound/audio for entry, confirm, or a new highscore fanfare** — no audio-synthesis engine exists anywhere in this codebase yet.
- **A timeout, auto-submit, or cancel path during initials entry** — the screen waits indefinitely for 3 confirmed letters; a future enhancement, not core arcade behavior this feature must ship.
- **Any change to `GameState`/`GameSession`'s three-value enum.** The initials-entry/top-5 screens are the consuming game's own private state, mirroring the WIN/LOSS `Outcome` precedent (`galactic-invasion` A3) exactly.
- **Any accessor on `GalacticInvasion` beyond the single score/outcome-report member (AC-5.2).** No lives, formation, or other internal state is exposed.
- **Choosing the storage mechanism itself (NVS vs. a raw flash partition, A5)** — a `/sprint-plan` technical decision, not a spec-level one.
- **A second real consuming game** (Steam Racer etc.) — API reusability is proven via a synthetic second identifier only (US-6), not a second real game shipping.
- **Resetting, clearing, or editing the persisted table from any in-game UI.**
- **Lowercase letters, digits, or symbols in initials** — A–Z only (A11).

## 8. Design Review

- **Overall impression:** The two new screens extend the codebase's one established screen convention (title-screen/galactic-invasion's end screens: `drawText`-only, font-metric-derived layout, `BRIGHT_ORANGE`-on-`BLACK`, `static_assert`-proven disjointness) to a 3-position cursor — no new drawing primitive is needed, and NFR-7's deliberately-open question (the active-letter indicator mechanism) has a concrete, precedent-consistent answer below. The two real gaps are learnability ones (nothing on either screen names *why* it appeared or *which* button does what) and one genuinely new layout situation this feature introduces that the existing font-metric convention doesn't obviously cover as written (a runtime-variable-width score string, where every prior screen's text was a compile-time-fixed literal). Neither is a Blocker; both are flagged below with a recommended fix or a PO follow-up.

- **Heuristics findings:**
  - **F1 — Recognition over recall: no on-screen label for the screen's purpose.** *Location:* US-2/AC-2.1 (initials-entry screen). *Rule violated:* "options visible, not memorized" — a returning player will infer "I got a high score" from context, but AC-2.1 as written puts only the raw score and three blank letter positions on screen, no text naming what's happening ("HIGH SCORE" / "ENTER INITIALS" or similar). Nothing in the 43-glyph charset (space, `!-.:0-9>?`, `A`-`Z`) blocks such a label — no lowercase or `=` is needed. *Fix:* add a short header label alongside the score. *This is new textual content, i.e. new scope — flagging to the PO via `/story-time` as a candidate AC addition, not adding it myself.* Severity: **Major**.
  - **F2 — Visibility of system status: a button press that silently does nothing.** *Location:* US-2/AC-2.4 (`input.start` "has no effect here"). *Rule violated:* a heuristic system tells the user what just happened; an ignored press should not be indistinguishable from an unresponsive device. `start` is the one button whose *name* suggests "begin/confirm," and this is the first screen in the shipped UI where pressing it produces zero visible effect (`title_screen.h`'s READY screen and both of galactic-invasion's end states all treat `start` as the expected, working action). A first-time player has no manual and no on-screen cue that this is intentional rather than a hang. *Fix:* either accept this silently (consistent with Principle 4's "no text the player must read"), or add a minimal on-screen control hint. *Flagging to the PO via `/story-time`* — resolving this by adding text is new scope; resolving it by leaving it as-is is a legitimate call the PO should make explicitly rather than have it fall out of a Designer's opinion. Severity: **Major**.
  - **F3 — Consistency: the one round with the best outcome is the only one that never shows WIN/LOSS.** *Location:* AC-2.1 vs. AC-4.1. *Rule violated:* same kind of event, same information should be shown. A non-qualifying round still renders "YOU WIN"/"GAME OVER" (AC-4.1, `galactic_invasion.cpp`'s existing `kWinText`/`kLossText`); a qualifying round's end screen is fully replaced by initials-entry (A8/C8, already resolved by the user) and AC-2.1 only requires the header to show the *score* — never the outcome. The player who just achieved a top-5 result is the one player who is never told whether that round was a win or a loss. *Not asking to reopen A8/C8* — it was an explicit, deliberate user resolution — but recording this as a residual question worth putting back to the PO: should the initials-entry header optionally carry the outcome text too, for parity with US-4's screen? New AC scope if yes; a conscious no-op if the PO reconfirms the existing wording. Severity: **Minor** (explicit resolved precedent, not an overlooked gap; recorded because the regression lands on the best-outcome case, not because it looks unintentional).
  - **F4 — User control: no way to correct an already-confirmed letter.** *Location:* US-2/AC-2.3, §6 Out of Scope ("no timeout, auto-submit, or cancel path"). *Rule violated (on paper):* "can they undo... without losing work" — once `fire` locks a position there is no back-navigation to it. *In practice:* this matches real coin-op cabinets of the era exactly (no backspace there either), which is consistent with Principle 3 ("own platform... not an emulator" is about *never chasing* historical accuracy, but doesn't forbid landing on the same answer for the same reason) and Principle 4 (arcade immediacy). Recording this as a deliberately-accepted tradeoff, not a required change. Severity: **Minor / informational**.

- **Accessibility notes:**
  - **Contrast:** already satisfied by inheritance — NFR-7 correctly reuses the `start-screen` NFR-7 precedent (`BRIGHT_ORANGE` on `BLACK` clears the 4.5:1 floor); no new finding.
  - **"Labels" (every input has one):** the three letter positions are the closest thing this device has to an interactive control, and per F1 above they carry no adjacent caption (only the bare score number gives context). Citing this once, under the base "every input has a label" checklist item rather than double-counting it against F1's heuristic framing — same underlying gap, same fix, same PO follow-up. Per the hard rule that accessibility findings are never Minor by default: Severity: **Major**.
  - **Focus order / visibility:** satisfied *once* the active-position indicator below is built — the cursor's order is fixed left-to-right across exactly 3 stops, always on-screen, never hidden. No independent finding beyond making sure the indicator ships (see Design risks).
  - **Touch targets:** N/A — this device has no touch surface at all (constitution §3: "the XPT2046 touch controller on the panel is deliberately unused"). Not a gap, correctly out of scope.
  - **Keyboard operability:** N/A in the literal sense (no keyboard exists on this platform, constitution §2); GameInput's 7 booleans are this device's only input surface, fully covered by AC-2.2/AC-2.3/AC-2.4.

- **Design risks & required changes:**
  - **R1 — NFR-7 resolution: the active-letter indicator.** *Recommendation:* a **static underline**, drawn with the *already-shipped* `-` glyph (font.cpp: a 5px horizontal bar at row 3 of its 8×8 cell) one `kGlyphHeight` row directly beneath the active letter position only — the other two under-letter cells are left undrawn (drawText's "off" pixels are already transparent, so there is nothing to erase there). Justification against the three options raised:
    - *Underline via `_`:* **not buildable as literally worded.** The shipped font is exactly 43 characters — space, `!-.:0-9>?`, `A`-`Z` (`font.h`/`font.cpp`) — and contains **no underscore**. NFR-7's own example text ("e.g. underline/inverted glyph") assumes a glyph that doesn't exist yet; adding one is a `font.cpp` change with its own compile-time art-validator and lint implications, out of proportion to this feature and out of this feature's stated scope. The `-` glyph is the closest already-shipped stand-in and satisfies the same visual intent.
    - *Inverted glyph (`fillRect` background + `BLACK` ink text):* technically buildable (`Framebuffer::fillRect` exists; `drawText`'s own contract already handles `ink == BLACK` specially), but it breaks the established convention that a pure-text screen composes `drawText` only — `title_screen.cpp` has a *structural* lint rule banning `setPixel`/`fillRect`/`blit` in that file (`tools/check_constraints.sh`, "title_screen.cpp draws only through drawText"), and AC-3.1 explicitly requires the top-5 screen to use "the shipped `drawText` only." Introducing `fillRect` on the sibling initials-entry screen would make the two new screens inconsistent with each other and with precedent for no real benefit. Also weaker on the letter of NFR-7 itself ("distinguishable without relying on colour alone") — a foreground/background swap within a single-hue 4-shade palette is still fundamentally a colour/luminance cue, not a shape cue.
    - *Blinking/flicker (mirroring `galactic-invasion` AC-10.8):* buildable, but two real drawbacks: (a) it makes the letter *currently being edited* disappear for half of every cycle, which is the one letter the player most needs to keep looking at; (b) this project's own QA method (constitution §8) is a **static framebuffer dump, one image per acceptance criterion** — a flicker-based cue is materially harder to verify from a single dump than a static glyph is, unlike AC-10.8's invulnerability flicker, which never needed AC-level single-frame verification of "is it currently visible."
    - The static-underline recommendation needs zero font changes, zero new drawing primitive, stays 100% `drawText`, and is exactly the mechanism NFR-7's own wording named first.
  - **R2 — the font-metric-derivation convention (CLAUDE.md) needs an explicit runtime-value addendum for this feature, not just a restatement.** Every existing screen's text is a **compile-time-fixed literal** (`"STEAMCORE"`, `"GAME OVER"`, `"SCORE: "` + a *zero-padded fixed-width* 4-digit value) — so `(sizeof(text) - 1) * kGlyphAdvance` is always a compile-time constant, and `static_assert` can prove disjointness directly. This feature's score display is the first screen-level text in this codebase whose width is only known **at runtime**: A14 fixed it at up to 5 digits, **unpadded** (0–99999), so `"12500"` and `"5"` render at different widths on different rounds. Neither AC-2.1 nor AC-3.1 says how layout should account for this. *Required for `/sprint-plan` to know before it writes tasks:* prove disjointness against the **worst-case (5-digit) width** at compile time (a `static_assert` using the maximum possible glyph count, exactly as `kScoreGlyphCount` already does for galactic-invasion's own fixed-width HUD score), then centre/position the *actual* shorter string at runtime within that already-proven-safe bound — never assume the compile-time convention applies verbatim to a value that isn't compile-time-known. Flagging this explicitly because CLAUDE.md's existing note ("Derive on-screen layout from font metrics, never a literal") is silent on the fixed-vs-variable-width distinction, and this is the first feature to hit it.
  - **R3 — the top-5 screen's 1-to-5-line layout needs a scalable disjointness proof, not N pairwise `static_assert`s.** `title_screen.h`/`galactic_invasion.cpp`'s disjointness proofs are each a single pairwise `static_assert` because each screen has exactly two elements. US-3's top-5 screen has a header **plus up to 5** occupied-rank lines (AC-3.1/AC-3.2) — a pairwise-comparison pattern doesn't scale cleanly to that. *Recommended for `/sprint-plan`:* derive every row's `y` from one shared row-pitch constant (`headerY + (rank_index + 1) * kGlyphHeight`, or similar) and prove the *general* invariant once — the header plus the maximum possible 5 rows all fit within `Framebuffer::height()` — rather than restating pairwise overlap checks per row pair. This keeps "disjoint by construction" instead of "disjoint by N asserted comparisons that must all individually stay in sync with the row count."
  - **R4 — both PO-follow-up flags from the heuristics findings, collected here for visibility:** F1 (no on-screen label naming the initials-entry screen's purpose) and F2 (no on-screen hint for the repurposed up/down/fire control scheme, and no feedback for the now-inert `start`). Both would require new textual AC scope if resolved by adding text; both are legitimate to resolve by *consciously* leaving as-is, given Principle 4's "no text the player must read to begin" — but that should be the PO's explicit call via `/story-time`, not an assumption baked in silently at `/sprint-plan` time.
