## 1. Problem & Goal

- **Problem:** The console's one playable game is visually anonymous. `GalacticInvasion::render` draws the engine's generic `drawTitleScreen` in `READY` (`galactic_invasion.cpp:144`), so the moment before play says `STEAMCORE`, not which game is about to start — and the concept art the user authored (`assets/sprites/galactic_invation.png`) has never reached the screen. The entire cast (`galactic_invasion_art.h`) is `' '`/`'#'` string rows typed by hand at `/increment` time, one flat ink per sprite. Constitution Principle 1 ("atmosphere beats capability") is the project's *first* principle, and today the game's atmosphere stops at the palette.
- **Goal:** Selecting the game shows **its own** logo; one press of the physical START button begins play; ship, enemy and shots share one designed look — derived from the concept sheet by a reproducible offline step wherever there is something to derive, so the next sprite costs a tool run instead of an hour of hand-transcription.
- **Success signal:** A host test renders `READY` and asserts the logo and the `PRESS START` prompt land at their documented, non-overlapping bounds with every other pixel `BLACK`, and that both are gone the tick after a START rising edge; every behavioural assertion of the shipped game (dimensions, collision, formation, scoring, lives, flow, determinism) still passes, textually unchanged; the build is green with `assets/` deleted. Hardware signal (US-4): a framebuffer dump shows the logo, and a human presses the real START button and is playing with the redrawn cast.
- **Why now:** The concept sheet, the shipped `Sprite`/`blit` path, the 4-colour palette and a released, playable game all already exist; this is the cheapest moment to close the gap between "the game works" and "the game looks like itself", and it settles the PNG-pipeline question `galactic-invasion` A14 deliberately left open ("A future feature may justify a PNG-to-`Color`-array conversion tool… but it isn't built now") with one small tool instead of re-litigating it per sprite.

## 2. Target Users

- **The console player (primary):** picks up the device, sees *which* game they are about to play, presses one button, and plays a round whose ship, enemies and shots look drawn rather than blocked out — and can tell at a glance which shot is theirs and which one is about to hit them. Directly testable end-to-end on the real hardware — START (GPIO47) and both analog axes work today.
- **The engine developer / future game author (secondary):** gets one documented, reproducible way to turn authored artwork into `constexpr` sprite data, instead of hand-transcribing every future sprite (Steam Racer, Airship Battle, Mine Runner each have their own concept sheets under `assets/sprites/`).
- *Not a user of this feature:* a player choosing among several games — no registry and no second game exist (`galactic-invasion` A8, `start-screen` A1). There are no roles, accounts or permissions anywhere in this product (constitution §2): one person at one cabinet, everything on screen visible to whoever is standing there.

## 4. User Stories

### US-1 (Must): The game announces itself with its own logo before play

> As the console player, I want the game I selected to show its own logo and wait for one button press, so I know what I'm about to play and start it without reading instructions.

**Acceptance criteria:**

- [ ] AC-1.1: Given `GameState::READY`, when the game's render step runs, then the `GALACTIC INVASION` logo is drawn via `Framebuffer::blit` at a fixed, documented bounding rectangle, and every pixel not covered by it or the prompt (AC-1.3) is `BLACK`.
- [ ] AC-1.2: Given the logo's pixel data, when inspected, then **each generated logo artefact is one rectangular sprite drawn by exactly one `blit`** (D9 — the one-blit rule scopes to the generated artefact, so the AC-1.11 fallback path, which adds font-drawn text beside the emblem, does not contradict it), at most 200×56 px overall, containing only the four palette `Color` values. No `fillRect`, no `setPixel`, no new drawing primitive.
- [ ] AC-1.3: Given the same `READY` state, when rendered, then `PRESS START` is drawn via the shipped `drawText` in `BRIGHT_ORANGE` at a fixed, documented bounding rectangle.
- [ ] AC-1.4: Given every element the `READY` screen draws — two rectangles on the normal path, three on the AC-1.11 fallback path (emblem, wordmark line(s), prompt) — when checked, then each lies fully within `Framebuffer::width()`/`height()` and **all pairs are disjoint**, proven **twice**: a header `static_assert` using the general four-way separating-axis expression per pair, and an independent runtime host test (CLAUDE.md layout convention). Every rectangle's width/height derives from the art's own dimensions and the font's metrics, never from literals.
- [ ] AC-1.5: Given `READY` and a rising edge of `input.start`, when the next tick renders, then neither the logo nor the prompt is drawn, and the round is in `PLAYING` — unchanged from the shipped `galactic-invasion` AC-6.2, with no new `GameState` value and no new `GameInput` field.
- [ ] AC-1.6: Given `input.start` stays `true` for several ticks after that edge, when each tick renders, then the logo never reappears; and given the same fixed input sequence run twice from a fresh game, the framebuffer sequence is byte-identical (constitution §4).
- [ ] AC-1.7: Given the logo's source region is the **tight crop of the two wordmark lines alone** — frame and gradient planet excluded (D7, A8) — when `/look-and-feel` reviews the result rendered at 1:1, then it reads as large-pixel art with clear shapes, carries a legible `GALACTIC INVASION` wordmark, and contains **no dither pattern** simulating intermediate tones (constitution §6). The fallback (AC-1.11) is judged only after this attempt has been rendered and looked at, never predicted from the sheet.
- [ ] AC-1.8: Given any state, when the logo-drawing step runs, then it **never clears the framebuffer** and never erases what it drew on a later tick — the game's own `render` owns the `fb.clear(BLACK)` it already performs (`galactic_invasion.cpp:141`), mirroring `drawTitleScreen`'s shipped contract; and it draws **nothing at all** in `PLAYING` or `GAME_OVER`, enforced by an exhaustive `switch` so a future `GameState` value fails to compile.
- [ ] AC-1.9: Given a freshly constructed game whose very first tick already has `start == true`, when that tick runs, then the shipped rising-edge rule applies unchanged (`game_state.h`) — play begins immediately and the logo is never rendered. Inherited behaviour, asserted by a host test so it is documented rather than discovered (A12); no debounce, dwell timer or release-first rule is added.
- [ ] AC-1.10: Given the host suite runs under `-fsanitize=address,undefined`, when the logo screen renders, then no out-of-bounds access occurs — the inherited `Framebuffer`/`blit` clipping contract, not re-implemented.
- [ ] AC-1.11: Given `/look-and-feel` judges the generated wordmark illegible at its rendered size, when the fallback is taken, then (i) **at least one generated artefact is still present** — the emblem becomes mandatory, so `READY` never degenerates into three lines of identical 8×8 text, i.e. the very screen US-1 replaces; (ii) the words are set on **two lines** (`GALACTIC` / `INVASION`, 64 px each) so the game's name outranks the 88-px prompt by block mass; (iii) their ink is **`BRIGHT_ORANGE`** — at 8×8 this is normal-size text, where `ORANGE` (4.35:1) misses the 4.5:1 floor (D8). Generated data is **never** hand-retouched (A11), and the fallback's rectangles obey AC-1.4's pairwise proof.
- [ ] AC-1.12: Given the `READY` screen's prompt, when its bounding rectangle is compared with the engine's shipped `kTitlePromptBounds` (`title_screen.h:89–96`), then the two are **identical** — same derivation, same glyph row, same centring — so "where the thing you press is announced" stays constant across both screens for the day a menu shows them in sequence (D12). Asserted by a host test comparing the two rectangles, not by restating a coordinate.

### US-2 (Must): The whole cast is redrawn from the designed artwork

> As the console player, I want the ship, the enemies and the shots to share one designed look, so the screen reads as one thing instead of a mix of styles — and so I can always tell my ship and my shot from theirs.

*Scope note (A15): the four sprites that already exist — player, enemy, projectile, enemy shot — are brought up to the new look at **unchanged** dimensions. No new entity, no new enemy type, no animation frame (§6).*

**Acceptance criteria:**

- [ ] AC-2.1: Given the player sprite's data, when compared to the concept sheet's player ship, then its silhouette is recognisably that ship (AC-2.5), within an unchanged **12×12** footprint — `kPlayerWidth`/`kPlayerHeight` keep their current values (A6).
- [ ] AC-2.2: Given the redraw changes pixel data and inks, when the shipped `galactic-invasion` suite runs, then **every behavioural assertion still passes textually unchanged** — dimensions and bounds, collision outcomes, formation stepping/reversal/descent, the single-active-projectile rule, scoring, lives/respawn/invulnerability, win/loss/restart flow, HUD disjointness, determinism. A test file may change **only** in *how it locates an entity* on screen (AC-2.8/AC-2.11) or in pinning concrete pixel patterns/inks (today `galactic_invasion_art_test.cpp`). If an expected *value or outcome* has to change to make a test pass, that is a defect in the redraw — a sprite whose geometry or behaviour moved — not a test to adjust.
- [ ] AC-2.3: Given any sprite's data, when inspected, then its outer silhouette carries its **side's identity ink** — `BRIGHT_ORANGE` for the player ship and player shot, `ORANGE` for the enemy body and enemy shot (A17/D3) — `BRIGHT_ORANGE` appears nowhere in enemy-side pixel data, and `DARK_ORANGE` appears only on interior pixels. A sprite **narrower than 3 px has no interior at all and therefore may not use `DARK_ORANGE`** (D6) — which is why both 2×6 shots are single-ink by construction, not by omission.
- [ ] AC-2.4: Given the redrawn player, enemy, projectile and enemy shot, when `/look-and-feel` reviews them, then (a) each is distinguishable from each of the others **by silhouette alone, with colour ignored entirely** — including the two 2×6 shots, which AC-3.10's segmented enemy silhouette separates (D5); the enemy's shape stays in the **opposite family from the player's** (horizontally elongated, not a nose-up wedge) and keeps **≥2 outline concavities** so its outline carries information at 12×10 (D10); and (b) the player ship stays identifiable at a glance **during play** — in motion, with several enemies on screen and shots in flight, not merely as a still pair side by side. Under A17's reserved inks, colour now supports (b); (a) must hold without it.
- [ ] AC-2.5: Given the redrawn ship on screen during play, when `/look-and-feel` reviews it, then it still reads as "the thing I steer" — nose-up, vertically symmetric, unambiguous against a moving formation.
- [ ] AC-2.6: Given each sprite at actual size, when shading is considered, then it is applied only where a measured ink step carries form: the player (12×12) may pair `BRIGHT_ORANGE` hull with one contiguous `DARK_ORANGE` interior mass ≥2×2 (6.18:1); the enemy (12×10) may carry at most one contiguous `DARK_ORANGE` core ≥3×3 and is otherwise **flat `ORANGE`** — a deliberate, recorded choice, not a shortfall (2.73:1, drawn 18 times at once); both 2×6 shots are **flat, single-ink, categorically** (§8). A three-step ramp inside any of these sprites is mottling, not modelling, and fails this criterion.
- [ ] AC-2.7: Given a redrawn sprite is not visibly better than the one it replaces at actual scale (`/look-and-feel` judgment), when that is found, then the shipped sprite is kept and the decision recorded — this feature does not churn released art for the sake of having regenerated it. §8 names where this is expected to bite: the **player shot** (twelve cells leave nothing to derive — keep the shipped bar) and the **enemy body** (its antennae/shoulder/legs are a strong small-size silhouette; adopt a derived version only if it keeps ≥2 outline concavities, else keep the shipped rows and bring them into the shading language by editing them — hand-authored art, so A11's no-hand-editing rule does not apply to it).
- [ ] AC-2.8: Given a test's colour-based entity locator lost its premise, when it is rewritten, then the replacement is **at least as discriminating as the one it replaces**. Scope after A17's reversal (D3) is narrowed but non-empty: `findProjectileTopY`'s `BRIGHT_ORANGE` scan *regains* its premise, since that ink is now player-exclusive — only its doc comment's stated reason changes (NFR-6), not its code; the **"any `DARK_ORANGE` pixel is an enemy shot" detector** (`galactic_invasion_round_test.cpp:212`, `galactic_invasion_dump_test.cpp:136`) loses its premise twice over — D4 moves that shot to `ORANGE`, and any sprite may now carry a `DARK_ORANGE` interior — and its replacement must separate the enemy shot from **enemy bodies**, which now share `ORANGE` (D5's segmented silhouette and the shot's own travel band are the available discriminators). A bare "any non-`BLACK` pixel in this region" substitution is acceptable only where the region is already proven to contain nothing else (as `findPlayerSpriteX`/`findFormationBounds` are, by compile-time-disjoint bands). Where no locator can discriminate, the fixture's stronger convention is used instead: build the expected frame independently and compare. The guarded assertion stays textually unchanged and the assertion count never shrinks.
- [ ] AC-2.9: Given the four sprites' dimension constants (`kPlayerWidth/Height`, `kEnemyWidth/Height`, `kProjectileWidth/Height`), when the diff is inspected, then none of their values changed (A6) — so no hitbox, formation pitch or screen-bound derivation moved.
- [ ] AC-2.10: Given `galactic_invasion_art_test.cpp`'s current guarantees (a sprite matches independently-restated art; `blit` leaves non-sprite background pixels untouched), when the `'#'`-string art it cross-checks is replaced or regenerated, then those guarantees are **replaced, not dropped** — dimensions and tight packing, palette-membership, AC-2.3's ink rule and `BLACK`-is-transparent blit behaviour stay asserted for every sprite — **plus four new structural assertions covering the reduction risks §8 found:** (i) the outermost lit ring of every sprite contains no `DARK_ORANGE` (D1); (ii) every sprite has a non-`BLACK` pixel in its first row, last row, first column and last column, and at least one `BLACK` pixel in its outer ring, so no sprite ships as a filled rectangle (D1/D2); (iii) no lit pixel lacks a 4-neighbour of its own ink and no `BLACK` pixel is fully enclosed by lit pixels — 1-px edge notches open to the outline stay allowed, being silhouette rather than noise (D11); (iv) no `BRIGHT_ORANGE` pixel exists in any enemy-side sprite (AC-2.3/D3).
- [ ] AC-2.11: Given any rewritten locator (AC-2.8), when it is reviewed, then it carries a **negative control**: a test showing it returns "not found"/fails when the entity it locates is absent or displaced. A rewritten test that would still pass with the entity missing is a broken test, not a migrated one. Required per rewritten locator — a set A17's reversal shrank to the enemy-shot detector and whatever else `/sprint-plan` finds, not a blanket sweep of the suite.
- [ ] AC-2.12: **Exercised 2026-09-15 (§8 D3), outcome user-confirmed (C28).** This AC granted `/look-and-feel` the authority to revert A17's full ink freedom to reserved inks on a recorded finding. The review exercised it and the reversal is now binding in AC-2.3/AC-2.4 and A17. The clause stays here as the record of *how* that reversal was reached — a spec-sanctioned path, not a late scope change — including the one place the review deviated from its own parenthetical: the enemy shot is `ORANGE`, not `DARK_ORANGE` (D4).

### US-3 (Must): Artwork is generated offline and the build never touches the PNG

> As the engine developer, I want sprite data produced from the concept sheet by one checked-in offline step wherever there is something to derive, so future artwork costs a tool run instead of hand-transcription — and so nothing the firmware builds or runs ever depends on an image file.

**Acceptance criteria:**

- [ ] AC-3.1: Given the committed concept sheet and a documented invocation naming each region to extract, when the generator is run, then for **every artefact it generates** it emits compile-time (`constexpr`) data quantised to exactly the four palette colours, in this project's existing `Sprite`/`Color` shape, subject to two policies §8 found missing and this AC now binds: **(a) a background rule** — a documented, deterministic rule (parameterised, recorded per AC-3.4, applied *before* quantisation) that maps the sheet's panel fill, vignette and glow halo to `Color::BLACK`, never to a foreground ink, so no artefact comes out as a filled rectangle with a dark halo (D1; the rule's mechanism — threshold, alpha, flood fill, chroma distance — is a `/sprint-plan` decision, its existence, determinism and documentation are not); and **(b) a fit policy** — sprites **fill their frozen box**, anisotropic scaling permitted, because the 12×12/12×10 hitbox is the design constraint and art that stops short of its edges makes hits read as unfair while AC-2.2 correctly reports no behaviour change; the **logo preserves its aspect ratio**, since squashed letterforms are unreadable (D2). Which artefacts are generated at all is settled per sprite by AC-2.7/AC-3.11, not fixed here (D13).
- [ ] AC-3.2: Given the repository with `assets/` removed entirely from the working tree, when `make test` and the ESP-IDF device build are run, then both succeed — no build step, test, or runtime path reads any `.png` (the invariant `galactic-invasion` A14 protected, A4).
- [ ] AC-3.3: Given the generator is run twice on the same source with the same parameters, when the outputs are diffed, then they are byte-identical — for **every** artefact it produces, including the background rule's effect (AC-3.1a), not just the first.
- [ ] AC-3.4: Given **each generated** file, when read, then it carries a machine-written provenance banner: "generated — do not edit by hand", the source file name, a content hash of the source, the extracted region, the **background-rule and fit parameters** (AC-3.1), the quantisation parameters and tie-break, and the exact command to regenerate it.
- [ ] AC-3.5: Given the generated data, when the project is compiled, then **each generated** artefact's dimensions, tight packing and palette-only content are validated by `static_assert` (the `galactic_invasion_art.h`/`font.cpp` convention), and all of it is `static`/`constexpr` read-only data — no dynamic allocation, no runtime decoding. Hand-authored sprites (AC-3.11) carry the identical `static_assert` set; only the provenance banner distinguishes the two routes.
- [ ] AC-3.6: Given the generator is run with (a) a missing or unreadable source file, (b) a region extending beyond the source image's bounds, (c) a target size **larger** than the source region (upscaling), or (d) an unwritable output path, when it exits, then it exits non-zero with a message naming which of these occurred — and no output file is written or partially overwritten. Best-effort silent fallback is forbidden for all four.
- [ ] AC-3.7: Given the generated art header, when it is `#include`d by the device-side harness and `idf.py build` runs, then the build is green — no `throw`, no reliance on transitively-included headers (CLAUDE.md: `text-rendering`'s host-only-module scar, caught two features late).
- [ ] AC-3.8: Given any source pixel that the background rule (AC-3.1a) did not map to `BLACK`, when the generator quantises it, then it maps to exactly one of the remaining palette colours by a total, deterministic rule whose tie-break is documented and applied identically on every run — an equidistant colour is never an error and never run-dependent (this is what makes AC-3.3 hold).

## 6. Out of Scope

- **Everything on the concept sheet that isn't an already-existing sprite:** additional enemy types (scout/fighter/bomber as *new entities*), the `Mothership` boss, power-ups, heart/life icons, digit art, background elements, explosion and particle art. A15 widened the redraw to the *existing* cast only — it added no entity. (The sheet's SCOUT/FIGHTER art may still serve as the *source region* for the one existing enemy, per D10.)
- **The logo's frame and gradient planet** (D7/A8) — the first attempt is the tight wordmark crop; a smooth sphere reduced to four inks without dithering is exactly the artefact AC-1.7 bans.
- **Animation of any kind:** multi-frame ship, enemy or logo animation, thruster flicker, explosions, logo fades or transitions (constitution §6). The existing invulnerability flicker (`galactic-invasion` AC-10.8) is unchanged, not extended.
- **Changing any sprite's dimensions** (A6, AC-2.9) — a hitbox change disguised as an art change.
- **Any gameplay, balance, scoring, lives or timing change.** This feature changes pixels, not rules — AC-2.2 is the fence.
- **Rewriting tests beyond entity location.** The locator rework (AC-2.8/AC-2.11) and pixel-pattern tests are the *only* sanctioned test changes; restructuring, renaming or "tidying" the suite while in there is not part of this feature.
- **Generating a sprite where generation adds nothing.** AC-2.7/AC-3.11 explicitly permit hand-authored art for the 2×6 shots and a kept enemy silhouette; forcing every sprite through the tool for uniformity's sake is not a goal (C32).
- **Changing `GameSession`'s rising-edge rule, or adding a debounce / minimum-dwell timer** to the logo screen (A12).
- **A general engine-level asset pipeline** for all games, an asset registry, or a shared `assets.h`. One tool, one game's art, one consumer (A2).
- **Runtime or build-time PNG decoding, and any image library in the firmware build** (A4, AC-3.2) — the line `galactic-invasion` A14 actually drew, kept.
- **Modifying or deleting `title_screen.h`/`.cpp` or their tests.** The engine's `STEAMCORE` screen stays intact for a future boot/menu feature; this game stops calling it (A1) but reuses its prompt geometry (AC-1.12).
- **A game-selection menu, a game registry, or a console boot screen** (`start-screen` A1, `galactic-invasion` A8); **re-showing the logo between rounds, a pause screen, or an attract mode** (A9); **`fire` or `select` as a confirm button** (A3).
- **Sound on the logo screen.** No audio engine exists anywhere in this codebase.
- **Committing `assets/fonts/` or `assets/Buttons.png`, or importing any `.ttf`** (A14) — font legibility remains the accepted risk `start-screen` A6 recorded.
- **Re-authoring the other games' concept sheets** (`steam_racer.png` etc.) with the new tool. Reusability is a by-product, not a deliverable.

## 8. Design Review

<!-- Filled by /look-and-feel. Empty design review = gate stays red for UI-facing features. -->

*Mode A, 2026-09-15. Reviewed: the committed sheet at actual target sizes, `galactic_invasion_art.h`, `font.h`/`text.h`, `title_screen.h`, `panel_format.cpp` (measured palette). Active design-relevant lenses: **none** (`ux`/`seo`/`i18n` off, constitution §2) — the on-device UI is judged against §6 and the base heuristics.*

- **Overall impression:** A well-fenced spec: the frozen dimensions (A6), the one-blit logo (AC-1.2), the "no PNG in the build" invariant (AC-3.2) and the anti-churn rule (AC-2.7) are all the right constraints, and AC-2.6's explicit permission for "flat is the correct answer" is unusually honest. **The one thing it does not yet acknowledge is what the source actually is.** The sheet is a *concept illustration* — smooth gradients, glow halos, a non-black brown panel background, a vignette, and a palette legend that is a claim rather than the file's content. The generator is therefore doing art **reduction**, not art **import**, and three of the four Blockers below are consequences of that single fact. Measured from `panel_format.cpp`: `BRIGHT_ORANGE` 9.86:1 on black, `ORANGE` 4.35:1, `DARK_ORANGE` **1.59:1**; between inks, `BRIGHT`↔`DARK` 6.18:1, `ORANGE`↔`DARK` 2.73:1, `BRIGHT`↔`ORANGE` **2.27:1**. Those three numbers decide most of what follows. Judged at real size: one virtual pixel is 2×2 panel pixels ≈ 0.31 mm ≈ 2 arcmin at 50 cm — at the edge of acuity, and below it on a moving sprite.

**Required changes — these block the gate until the PO folds them in.**

- **D1 (Blocker) — No transparency rule: every generated sprite comes out as a filled rectangle with a dark halo.** *Location:* AC-3.1/AC-3.8, all five artefacts. *Rule:* §6 "clear silhouettes"; AC-2.3 (`DARK_ORANGE` never on an outer silhouette). *Evidence:* on the sheet the sprites sit on a mid-brown panel fill with a vignette and each carries a soft glow. "Map any source pixel to the nearest of the four palette colours" (AC-3.8) maps that background to `DARK_ORANGE`/`ORANGE` — a 12×12 crop yields a solid block, and the glow becomes a dark halo on the outline. *Fix:* AC-3.1/AC-3.8 gain a documented, deterministic **background rule** — which source pixels become `Color::BLACK` — specified, parameterised and recorded in the provenance banner (AC-3.4) exactly like the tie-break, and applied before quantisation. Add to AC-2.10's assertion set: the outermost lit ring of every sprite contains no `DARK_ORANGE`.
- **D2 (Blocker) — Fit policy is unspecified, so the ship will look smaller than its hitbox.** *Location:* AC-3.1 (no fit/aspect policy anywhere), AC-2.1/AC-2.9, player + enemy. *Rule:* error prevention / match to the real world — collision is the frozen 12×12 rect (A6), so art that doesn't reach the box edges makes hits read as unfair and silently moves *perceived* balance while AC-2.2 correctly reports "no behaviour change". *Evidence:* the sheet's IDLE ship is ≈0.7:1; an aspect-preserving fit into 12×12 leaves ~2 blank columns per side. The shipped art holds the invariant today (`galactic_invasion_art.h:38–64`: every sprite touches all four box edges). *Fix:* state the policy per artefact in AC-3.1 — **sprites fill their box** (anisotropic fit permitted; the 12×12 box, not the sheet's proportions, is the design constraint), **the logo preserves aspect** (squashed letterforms are unreadable). Add to AC-2.10: every sprite has a non-`BLACK` pixel in its first row, last row, first column and last column.
- **D3 (Blocker) — AC-2.12 is exercised: A17 is reverted to reserved inks.** *Location:* AC-2.4b/AC-2.12, whole cast. *Rule:* §6 clear silhouettes + NFR-7 ("identity must survive colour being ignored"); pop-out requires one side to own a feature value exclusively. *Evidence:* 18 enemies (3×6, `galactic_invasion.h:62`) against one ship. The positional cue that would replace colour — "mine is the one at the bottom" — is guaranteed to fail at exactly the two moments it matters: when the formation descends toward `kFormationThresholdY`, and during respawn invulnerability flicker (`galactic-invasion` AC-10.8), when the player's own ship is intermittently absent. And under A17 an enemy shot may be `BRIGHT_ORANGE`, i.e. identical in ink to the player's own shot mid-flight — "am I about to hit or about to be hit" becomes unreadable. The inks are too close to carry identity *jointly* (`BRIGHT`↔`ORANGE` = 2.27:1, under the 3:1 floor); they only work if each side owns one. *Fix (binding):* (i) `BRIGHT_ORANGE` appears in the player ship and player shot **only** — nowhere in enemy-side pixel data; (ii) enemy body and enemy shot carry an `ORANGE` outer silhouette; (iii) `DARK_ORANGE` is interior depth only, in sprites ≥3 px wide, never on an outer silhouette. *Note this costs almost no atmosphere:* coherence across the cast comes from a shared **shading language** (identity ink outside, one contiguous `DARK_ORANGE` mass inside), not from a shared ink set — which is what C23's "a shaded ship next to flat enemy art falls apart" actually asks for. The player keeps all three inks; only the *enemy's* access to `BRIGHT_ORANGE` is withdrawn.
- **D4 (Blocker, accessibility) — The enemy shot is a lethal object at 1.59:1.** *Location:* AC-3.10/A16, `kEnemyShotSprite`. *Rule:* contrast — `DARK_ORANGE` (#4D2600) on black measures **1.594:1**, below the 3:1 floor for graphical objects, on a sprite that is 2×6 virtual px ≈ 0.6 × 1.9 mm on the panel at ~50 cm. The one thing the player must react to is the one thing they cannot see. *Fix:* the enemy shot uses `ORANGE` (#B35900, **4.35:1**); AC-3.10's `DARK_ORANGE` is replaced. This deviates from AC-2.12's parenthetical ("enemy shot `DARK_ORANGE`") on purpose — that clause would pin the hazard to the palette's least visible ink. Everything else in AC-2.12's reversal stands.
- **D5 (Major, PO decision) — The two 2×6 shots cannot be separated by silhouette while AC-3.10 mandates an identical one.** *Location:* AC-2.4a, NFR-7. *Rule:* NFR-7, "entity identity must survive colour being ignored entirely" — same size, same shape, same 12 cells means identity rests on ink (a 2.27:1 step) plus direction of travel alone. *Fix — the PO picks one; the spec must not stay self-contradictory:* **(a)** give the enemy shot a **segmented** silhouette (e.g. two 2×2 blocks with a 1-row gap) against the player's solid 2×6 bar — colour-independent, 12 cells, no dimension change; or **(b)** record an explicit, reasoned NFR-7 exception for this one pair, on the grounds that origin and travel direction carry the read in motion. I recommend (a). It overturns A16/AC-3.10's "same silhouette", which is the PO's ruling — hence a question, not a change I make.
- **D6 (Major) — AC-2.3 is unsatisfiable for 2-px-wide sprites, and AC-2.10 will fail the build on it.** *Location:* AC-2.3 vs AC-3.10, both shots. *Rule:* a 2-px-wide sprite has **zero** interior pixels — every lit pixel is on the outer silhouette — so "`DARK_ORANGE` only on interior pixels" forbids it outright there, while AC-3.10 requires it; AC-2.10 orders that limit `static_assert`ed for *every* sprite, so the shipped enemy shot fails the check the spec itself commissions. *Fix:* restate AC-2.3 — "…and a sprite narrower than 3 px has no interior, so it may not use `DARK_ORANGE` at all". D4 then settles the ink.
- **D7 (Major) — Crop the logo to the wordmark, or the AC-1.11 fallback becomes self-inflicted.** *Location:* AC-1.7/AC-1.11/A8. *Rule:* AC-1.7 ("large-pixel art with clear shapes, no dither") and A8's "a visible reduction beats a failed downscale". *Numbers:* the framed artwork is ≈2.1:1; aspect-fitted into ≤200×56 it lands at ~115×56 — cap height ~14 px, strokes ~3 px, with the letterforms' dark outline and inner bevel both sub-pixel and quantising arbitrarily into the strokes. Cropped to the **two wordmark lines alone** the block is ≈2.9:1 → ~159×56 — cap height ~20–22 px, strokes ~5 px, counters ~5 px. *Fix:* AC-1.7's first attempt is specified as the tight wordmark crop, excluding the frame and the large gradient planet (A8 already permits this: a smooth sphere reduced to 4 inks *without dithering* becomes hard concentric banding plus speckle, precisely the artefact AC-1.7 bans). Judge the fallback only after that attempt.
- **D8 (Major) — On the fallback path the emblem stops being optional, and the fallback's ink must be pinned.** *Location:* AC-1.11 (+AC-1.2/AC-1.3). *Rule:* hierarchy (the eye must land on the game's name first) and contrast. *Evidence:* AC-1.11's `drawText` fallback plus A8's "frame/planet optional" together permit a `READY` screen that is three lines of identical 8×8 `BRIGHT_ORANGE` text — indistinguishable in character from `drawTitleScreen` (`title_screen.h:80–96`), i.e. the exact screen US-1 exists to replace, with the game's name set at the same weight as the prompt. *Fix:* (i) at least one generated artefact must be present — if the wordmark falls back, the emblem becomes **mandatory**; (ii) the fallback wordmark is set on two lines (`GALACTIC` / `INVASION`, 64 px each) so it outranks the 88-px prompt by block mass; (iii) its ink is pinned to `BRIGHT_ORANGE` — at 8×8 it is normal-size text, where `ORANGE` (4.35:1) misses the 4.5:1 floor. AC-1.3 pins this for the prompt; AC-1.11 leaves it open.
- **D9 (Major) — AC-1.2 and AC-1.11 contradict each other.** *Location:* AC-1.2 ("exactly one `blit`, not a composition") vs AC-1.11/AC-1.4. *Rule:* consistency — a gate criterion that cannot hold on a spec-sanctioned path is not a criterion. *Fix:* scope AC-1.2's one-blit rule to *the generated artefact*, and state that on the fallback path AC-1.4's disjointness proof runs pairwise over three rects (emblem, wordmark line(s), prompt), not two.

**Recommendations (non-blocking).**

- **D10 (Minor) — Enemy source region: SCOUT or FIGHTER, never BOMBER.** The sheet's BOMBER is a nose-up, vertically symmetric winged ship — the *same* shape family as the player, which the shipped art deliberately avoided (`galactic_invasion_art.h:18–24`, "the opposite shape family from the ship"). FIGHTER is preferable to SCOUT: its wing notches give the outline the concavities a convex 12×10 diamond lacks.
- **D11 (Minor) — Minimum feature size 2×2; no enclosed 1-px holes.** At 2 arcmin per virtual pixel an isolated lit pixel on black is indistinguishable from a stuck sub-pixel, and an enclosed black pixel inside an orange mass from a dead one. *Fix:* add to AC-2.10 — no lit pixel without a 4-neighbour, no fully enclosed `BLACK` pixel. Edge notches 1 px wide and open to the outline stay allowed; they are silhouette, not noise.
- **D12 (Minor, consistency) — Put the prompt where the engine already puts it.** The shipped screen derives its prompt at `14 * kGlyphHeight`, horizontally centred (`title_screen.h:89–96`). Deriving the game's prompt identically, with the logo at `y = 4 * kGlyphHeight` (a 56-tall logo then ends on glyph row 11, 24 px above the prompt), keeps "where the thing you press is announced" constant for the day a menu shows both screens.
- **D13 (Minor, PO question) — Artefact count drifts once AC-2.7 and D4/D5 bite.** If the player shot is kept unchanged and the enemy shot is hand-decided, AC-3.1's "four regions, five artefacts" and AC-3.10 stop describing what ships. Restate AC-3.1 over *the artefacts that are generated*, and say what AC-3.4's provenance banner means for a sprite deliberately not generated.

**AC-2.6 — does shading carry? Per sprite, at actual size:**

- **Player 12×12 — yes, with one pair only.** Use `BRIGHT_ORANGE` hull + one contiguous `DARK_ORANGE` interior mass ≥2×2 (canopy/spine): 6.18:1, reads as form. `ORANGE` as a mid-tone between them is a wasted ink here — the two steps are 2.27:1 and 2.73:1, both under the 3:1 floor, so a three-step ramp inside 144 px reads as mottling, not modelling.
- **Enemy 12×10 — effectively flat, and that is the right answer.** Under D3 the enemy's only available pair is `ORANGE`↔`DARK_ORANGE` = 2.73:1, below the floor, on a sprite drawn 18 times simultaneously. Permitted: exactly one contiguous `DARK_ORANGE` core ≥3×3 (the pod). Anything finer: flat `ORANGE`, recorded as a deliberate choice per AC-2.6's own wording, not a shortfall.
- **Player shot 2×6 and enemy shot 2×6 — flat, one ink, categorically both.** Twelve cells, zero interior pixels (D6), and the sprite travels several px per tick, so a second ink reads as flicker rather than form. **This is the correct design, not a failure to shade.**

**AC-2.7 — where I expect the shipped sprite to be kept:**

- **Player shot — keep the shipped bar.** The sheet's shot is a tapered lens; across 2 columns a taper can only be expressed as a black corner cell, which on a 6-px column in motion reads as a dead pixel (D11), not a point. Twelve cells leave nothing to derive.
- **Enemy shot — not an AC-2.7 case.** It changes for D4 (ink) and possibly D5 (silhouette) — design decisions, not "regenerated art that came out better".
- **Enemy 12×10 — genuine risk of an AC-2.7 hit.** The shipped invader's antennae, shoulder notch and legs are a strong small-size silhouette; a downscaled sheet scout is a convex diamond carrying information only in its outline curvature. Adopt the redraw only if it keeps ≥2 outline concavities (D10); otherwise keep the shipped silhouette and bring it into the shading language by editing its `'#'` rows — that art is hand-authored, not generated, so A11 does not apply to it.
- **Player ship and logo — no AC-2.7 risk.** The shipped ship is a plain filled triangle with no wings; almost anything derived from the sheet beats it, and there is no shipped logo to compare against.

**Answers to the two remaining questions the spec puts to this review:**

- **AC-2.4a (pairwise silhouettes):** player (12×12, nose-up triangle) vs enemy (12×10, horizontally elongated) — **passes**, provided D10 and D2 hold. Player/enemy vs either shot (2×6) — **passes** on aspect ratio alone. Player shot vs enemy shot — **fails today and under the spec as written**; see D5.
- **AC-1.7/AC-1.11 (logo fallback likelihood):** **not the default outcome, but a real one.** With the framed, planet-bearing composition as the region it is near-certain; with the tight wordmark crop of D7 I expect the generated wordmark to hold at ~20–22 px cap height. Decide it on a rendered 240×160 dump at 1:1, never on the sheet.

- **Accessibility notes:** No keyboard, pointer or touch surface exists (the XPT2046 controller is off-limits, constitution §3), so focus order, keyboard operability and touch-target checks are **N/A by platform**, not skipped — same standing as `start-screen` §8. The axes that do apply are contrast and colour-independence, and both produced findings: **D4** (a lethal 2×6 object at 1.59:1, below every floor), **D8(iii)** (unpinned 8×8 fallback text where `ORANGE` misses 4.5:1), and **D3/D5** (NFR-7's "identity survives colour being ignored" — carried for the three larger sprites by silhouette, *not* carried for the 2×6 pair by any means). AC-1.3's `BRIGHT_ORANGE` prompt (9.86:1) and AC-2.3's letterform ban on `DARK_ORANGE` are correct as written and are checked off here, not restated. The wordmark at ~20 px cap height is large text, so `ORANGE` strokes (4.35:1) clear the 3:1 large-text floor — but I recommend `BRIGHT_ORANGE` as the dominant stroke ink anyway, so the game's name outranks the prompt in the hierarchy instead of tying with it.

- **Design risks & required changes:** **Required changes: D1, D2, D3, D4, D6, D7, D8, D9** (D5 and D13 are required *decisions*, and they are the PO's, not mine). **Gate verdict: red** — not because the spec is weak, but because D1/D2 are unstated generator contracts without which the first `/increment` produces orange rectangles, and D3/D4/D6 are readability and contrast defects the spec already hands this review the authority to settle. Residual risks worth carrying forward rather than fixing: the glow halo and starfield may still leave stray lit pixels adjacent to letterforms even with D1 in place — a single stray pixel next to a glyph reads as a rendering defect, so check for it on the 1:1 dump; and A12's accepted "START held at boot ⇒ the logo is never seen" remains accepted, with no action, since §6 rules out the only fixes. **Questions back to the PO (do not change scope on my say-so): D5** (differentiate the enemy shot's silhouette, or record an explicit NFR-7 exception?) and **D13** (how do AC-3.1/AC-3.4/AC-3.10 read once a sprite is deliberately not generated?).
